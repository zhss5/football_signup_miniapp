# V0.9.4 To Version 2 CloudBase Upgrade Rehearsal

- Date: 2026-07-29
- Baseline tag: `0.9.4`
- Target branch: `codex/version-2-web-admin`
- Rehearsal environment: `cloudbase-miniapp-test-dfc753877`
- Production environment: never use it while executing this rehearsal

## 1. Purpose

This runbook verifies that an existing V0.9.4 CloudBase deployment and its data
can be upgraded to Version 2 without losing Version 1 data or breaking a
Version 1 mini-program client during the rollout window.

The rehearsal reuses the existing test CloudBase environment. It does not
delete or recreate the CloudBase environment itself. It restores the
environment to a representative V0.9.4 baseline and then applies the same
ordered upgrade steps intended for production.

An empty database is not a valid migration rehearsal. It verifies only a new
installation. The rehearsal must import a V0.9.4-compatible data snapshot that
contains representative users, activities, teams, registrations, proxy
registrations, cancelled registrations, and notification subscriptions where
available.

## 2. Scope And Non-Goals

The rehearsal covers:

- backup and recovery readiness;
- V0.9.4 data restoration;
- V0.9.4 client smoke testing;
- additive Version 2 collection bootstrap and index creation;
- compatibility-first cloud-function deployment;
- Version 1 client regression against the Version 2 backend;
- Version 2 mini-program and Web Admin smoke testing;
- data integrity checks and rollback decisions.

The rehearsal does not:

- migrate runtime storage to MySQL;
- dual-write CloudBase and MySQL;
- switch traffic to a self-hosted HTTP API;
- automatically transform all historical documents;
- delete the CloudBase environment ID, static-hosting configuration, or domain
  binding.

## 3. Safety Gates

Do not start destructive test-environment work until all gates are satisfied:

- confirm the selected environment ID is exactly
  `cloudbase-miniapp-test-dfc753877`;
- confirm no production, review, trial, or developer build that matters is
  currently using this environment;
- announce a maintenance window for the test environment;
- export the current test data and Cloud Storage objects before clearing
  anything;
- record collection counts, indexes, database rules, storage rules,
  cloud-function permissions, authentication settings, and static-hosting
  configuration;
- keep real template IDs, secrets, local environment files, and credentials
  outside Git;
- identify one operator and one reviewer for every destructive console action.

Stop the rehearsal if the environment identity, backup completeness, or restore
procedure cannot be proven.

## 4. Back Up The Current Test Environment

Create a dated backup package outside the repository.

Back up:

1. Every current collection, not only the four Version 1 collections.
2. Cloud Storage files and a manifest containing object paths, sizes, and
   content types.
3. Collection indexes and database security rules.
4. Storage security rules.
5. Cloud-function names, runtime versions, environment variables, invocation
   permissions, and remote modify times.
6. Static-hosting files, domain bindings, and cross-origin/security-domain
   settings.
7. Authentication settings and Web SDK function permission rules.
8. Subscription-message template keys and IDs without committing them.

Record document counts for at least:

- `users`;
- `activities`;
- `activity_teams`;
- `registrations`;
- `activity_logs`;
- `user_role_logs`;
- `notification_logs`;
- `notification_subscriptions`;
- `web_admin_sessions`.

Perform a restore spot-check before clearing the environment. A backup that has
not been read back is not sufficient rollback evidence.

## 5. Restore A Representative V0.9.4 Baseline

### 5.1 Preserve The Environment

Do not delete the CloudBase environment. Keep its environment ID, billing
configuration, static-hosting service, and domain configuration.

Clear application data only after the backup gates pass. Restore the four
Version 1 business collections from the same snapshot:

- `users`;
- `activities`;
- `activity_teams`;
- `registrations`.

Use one consistent snapshot time for all four collections. Do not combine
collections exported at different times.

To exercise the missing-collection bootstrap path, remove the Version 2-only
collections from the rehearsal baseline:

- `activity_logs`;
- `user_role_logs`;
- `notification_logs`;
- `notification_subscriptions`;
- `web_admin_sessions`.

If the Version 2 collections cannot be removed, the rehearsal can still verify
bootstrap idempotency, but it cannot prove collection creation from a true
V0.9.4 state. Record that limitation.

### 5.2 Use An Isolated V0.9.4 Worktree

detached worktree:

### 5.3 V0.9.4 Baseline Smoke

Capture the resulting document counts and IDs. Either restore the original

## 6. Apply The Version 2 Upgrade

### 6.1 Local Verification

Return to the Version 2 branch and verify the worktree:

```powershell
git status --short --branch
npm ci
npm test
git diff --check
```

Do not stage or commit local CloudBase environment files.

### 6.2 Wave 1: Additive CloudBase Readiness

Deploy and invoke the idempotent bootstrap:

```powershell
npm run deploy:v2-bootstrap -- -EnvId 'cloudbase-miniapp-test-dfc753877'
```

Verify that the response reports the five Version 2 collections under
`created`, or under `existing` on a repeated invocation:

- `activity_logs`;
- `user_role_logs`;
- `notification_logs`;
- `notification_subscriptions`;
- `web_admin_sessions`.

The bootstrap must not delete, truncate, rename, or recreate the Version 1
business collections.

Create and verify the indexes from `docs/cloudbase/indexes.md`:

- `activities`: `status + startAt`;
- `activities`: `organizerOpenId + startAt`;
- `activity_teams`: `activityId + sort`;
- `registrations`: `activityId + status`;
- `registrations`: `userOpenId + status`;
- `registrations`: `userOpenId + updatedAt`;
- `activity_logs`: `activityId + createdAt`;
- `notification_subscriptions`: `activityId + templateKey + status`;
- `notification_logs`:
  `activityId + notificationType + recipientOpenId + status`.

### 6.3 Wave 2: Version 1-Compatible Backend

Copy shared helpers before packaging functions:

```powershell
npm run copy:cloud-shared
```

Deploy all Version 1-existing functions changed by Version 2 as one controlled
wave:

```text
addProxyRegistration
cancelRegistration
createActivity
ensureUserProfile
getActivityDetail
joinActivity
listActivities
moveRegistration
notifyActivityParticipants
removeRegistration
updateActivity
```

Deploy each function from its own function directory with `--dir .`. Verify
remote `CodeInfo`; repository-root relative deployment has previously uploaded
stale source in this CLI environment.

Do not proceed to Version 2 clients until the V0.9.4 mini-program passes the
following compatibility gate against these functions:

- missing `activityType` is treated as `internal`;
- missing `lateCancellationNoticeWindowHours` is treated as `6`;
- a V0.9.4 update that omits new fields preserves the stored Version 2 values;
- legacy `signupLimitTotal` activities still load and accept valid operations;
- additive response fields do not change the fields consumed by V0.9.4;
- existing users, activities, teams, and registrations remain readable;
- join, cancel, proxy signup, remove, move, create, edit, and notifications
  still work.

If this gate fails, stop and roll back the affected function wave before
deploying Version 2-only functions or clients.

### 6.4 Wave 3: Version 2-Only Backend

Deploy the remaining Version 2 function set from the handoff document,
including:

- `bootstrapV2Collections`;
- role and user management;
- attendance and statistics;
- roster export;
- activity logs and notification logs;
- manager aliases and self-registration profile updates;
- activity copy support;
- Web Admin QR login functions.

Seed the first `super_admin` only after confirming the target real mini-program
user document:

```json
{
  "roles": ["user", "super_admin"]
}
```

Do not grant privileged roles to an anonymous Web SDK identity.

### 6.5 Wave 4: Version 2 Clients

1. Upload a Version 2 mini-program experience build connected to the rehearsal
   environment.
2. Deploy Web Admin static files to `/admin/`.
3. Advance all Web Admin CSS and JavaScript asset version query tokens together
   before hosting deployment.
4. Verify the hosted page loads the intended asset versions.
5. Complete real-device QR login through the mini-program My page.

## 7. Version 2 Acceptance Matrix

### 7.1 Core Compatibility

- Existing V0.9.4 users can open the Version 2 mini program.
- Existing activities preserve title, time, venue, teams, capacities, and
  registrations.
- Historical documents without Version 2 fields receive API defaults rather
  than destructive backfills.
- A Version 1 client can still perform its supported workflows while Version 2
  functions are deployed.

### 7.2 Registration And Bench Queue

- regular capacity and bench capacity are calculated correctly;
- a stale bench signup request enters an available regular team;
- regular cancellation or organizer removal promotes the earliest eligible
  bench registration;
- proxy bench signup follows the same regular-capacity-first rule;
- generic team movement cannot move a registration into or out of the bench;
- self-registration profile edits stop at activity start.

### 7.3 Admin, Audit, And Statistics

- role boundaries work for `user`, `organizer`, `admin`, and `super_admin`;
- attendance updates and attendance statistics work;
- cancellation statistics and rates use the final per-activity outcome;
- roster CSV and XLSX exports contain every row and include activity type;
- activity logs show both current `targetOpenId` and legacy `userOpenId`
  records;
- fixed 20-row pagination does not omit later users, activities, statistics,
  or notification logs.

### 7.4 Notifications

- registration-threshold and late-cancellation subscriptions are independent;
- the late-cancellation window uses the current activity value;
- zero disables the late-cancellation notice;
- the late-cancellation recipient is the activity creator;
- participant display name prefers `managerAlias`, then `signupName`;
- notification payloads and logs use the correct template key and recipient.

### 7.5 Web Admin

- QR challenge creation, confirmation, and polling work;
- successful login hides the QR login view;
- ordinary users cannot enter the workspace;
- role-specific menus and API authorization agree;
- `listUsers` and `listActivities` load at least one complete page;
- activity detail, attendance, exports, and logs load without indefinite
  spinners;
- CSV and XLSX exports open with separate columns.

## 8. Data Integrity Checks

Compare pre-upgrade and post-upgrade data before production approval:

- document counts for the four Version 1 business collections;
- activity-to-team and activity-to-registration relationships;
- `registration.teamId` values that reference no activity team;
- duplicate active registrations for one real user and activity;
- valid registration status and attendance enum values;
- activity capacity against regular and bench registration counts;
- user roles normalized to include `user`;
- timestamps that are missing or have incompatible types;
- notification and activity-log target identity fallback fields.

Expected smoke-test mutations must be listed separately. Unexplained count
differences or orphan references block production rollout.

## 9. Rollback

Prefer code rollback over data rollback because Version 2 schema changes are
additive.

If the Version 1 compatibility gate fails:

1. stop test traffic;
2. redeploy the affected V0.9.4 cloud functions from the isolated baseline
   worktree;
3. restore the V0.9.4 mini-program test build if required;
4. leave additive Version 2 collections in place unless they caused the
   failure;
5. verify the V0.9.4 smoke matrix again.

Do not restore a database snapshot merely to remove harmless Version 2 fields
or empty Version 2 collections.

Use data restore only when documents were deleted, corrupted, or transformed
incorrectly. In that case, restore `users`, `activities`, `activity_teams`, and
`registrations` from the same snapshot while writes are stopped. Never restore
one related collection from a different snapshot time.

Web Admin can be rolled back independently by restoring the previous static
hosting package. Notification-template and permission changes must also be
reverted explicitly if they caused the failure.

## 10. Production Readiness Decision

Production upgrade is approved only when:

- the complete rehearsal has been run from a V0.9.4-compatible data snapshot;
- V0.9.4 passes before and after the compatibility backend wave;
- Version 2 mini-program and Web Admin acceptance passes;
- backups and restore evidence are available;
- no unexplained data-integrity difference remains;
- production deployment commands and function packages match the rehearsed
  versions;
- monitoring, maintenance window, operator, reviewer, and rollback owner are
  assigned.

Repeat the same order in production:

1. backup and freeze high-risk changes;
2. bootstrap collections and create indexes;
3. deploy the Version 1-compatible backend wave;
4. smoke the currently released Version 1 client;
5. deploy Version 2-only functions;
6. release Version 2 clients and Web Admin;
7. monitor function errors, notification failures, counts, and audit logs.
